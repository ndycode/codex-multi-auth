# v2.10.0

A pinned account now gets a real retry instead of one attempt, a pin is no longer starved by a load-spreading heuristic it cannot benefit from, and a new opt-in guard can pause a session before it overflows the model's context window. Nothing to migrate — install and go.

```bash
npm i -g codex-multi-auth
```

## What was wrong

**A pinned account got exactly one upstream attempt.**

`codex-multi-auth switch <n>` and `--account` pin every request to one account. That account has nowhere to rotate to, so when a request to it failed transiently — a 503, a socket reset — the sensible thing is to try it again. The retry budget existed and was never spendable.

Every transient branch in the rotation proxy's retry loop cools the account down before it continues: 4 seconds for a 5xx, 6 seconds for a transport error, an auth cooldown after a failed token refresh. Account selection then refuses a cooling-down pin. So the loop set a cooldown, asked for the account back, was told no, and gave up. One upstream call, then a `codex_pinned_account_unavailable` 503, for a fault that would have cleared on the next try.

**A pin was blocked by a bucket built for a pool it is not in.**

Each account carries a local token bucket that spreads load across the *selectable* pool. A pinned request has no alternative account, so a drained bucket could only ever reject a request the pinned account was able to serve. A busy pinned session hit `token-exhausted` and got a 503 while the account itself was healthy.

**`account_skip_reasons` could name a blocker that did not block.**

The pool-exhausted and pinned-unavailable payloads carry a per-account reason so `codex-multi-auth rotation status` can explain a refusal. The admission check has two gates — the token bucket and the circuit breaker's race-safe probe slot — and the reason was re-derived afterwards from account state rather than taken from the gate that rejected. It reported the *first* blocker it found, so an account with a live cooldown that actually failed on a drained bucket was reported as cooling down, and a rejection from a half-open breaker whose probe another request had just claimed was reported as an exhausted bucket.

## What's fixed

**A pinned request retries within a bounded budget.** Up to four upstream attempts, spaced 250ms, 500ms and 1s apart, under an absolute 16-pass ceiling over the selection loop. The budget is `min(retryAllAccountsMaxRetries + 1, 4)`: that setting is the "retry when every account is rate-limited" pool knob, and for a pin every unit of it would be another copy of the same non-idempotent request, so it is capped rather than spent one-for-one.

The retry waives the pinned account's own **cooldown**, and only the cooldown. A cooldown keeps *other* requests off a flaky account; a retry budget gives *this* request another attempt. Everything else still stops the retry:

| Blocker | Still refuses a pinned retry |
| --- | --- |
| Rate limit (429, quota) | yes — bounded by the upstream reset, so it belongs in the 503's `retry_after_ms` |
| Open circuit breaker | yes — three failures open it, which is what ends a 5xx storm |
| Disabled account, no enabled workspace | yes |
| Policy block (pause, drain, budget) | yes |
| The pin's own cooldown, from the second pass on | waived |

The cooldown itself stays on the account for every other request and still sets the 503's `retry_after_ms`. The waiver applies only from the second selection pass of one request, so a pin that was *already* cooling down when the request arrived is still refused without an upstream call.

**A pinned request no longer debits the pool token bucket.** Circuit-breaker admission still applies. The bucket is neither consumed nor refunded for a pin, so a pinned failure cannot mint tokens the pool never issued.

**A refusal names the gate that refused it.** The admission check returns its verdict directly — `token-exhausted` or `circuit-open` — instead of the reason being re-derived from account state afterwards. That also removes a state mutation from a hot read path.

## Added

**Context Budget Guard (experimental, ships disabled).**

Enable it from Settings → Experimental, or set `contextBudgetGuardEnabled` in `settings.json`.

A Responses session mostly resends its whole conversation every turn, so each turn's `input_tokens` plus the part of its output that becomes history is a live read of how full the context window already is. (`total_tokens` is deliberately not used: it also counts reasoning tokens, which are dropped rather than resent.) The guard tracks that per session and, once it crosses the hard threshold, answers the **next** request locally with a notice suggesting `/compact` or `/clear` — before the request costs an upstream round-trip, instead of waiting for the eventual `context_length_exceeded` 400.

| Capability | What it gives you | Configure via |
| --- | --- | --- |
| Soft threshold (default 65%) | A non-blocking `x-codex-context-budget-percent` response header | `contextBudgetGuardSoftPercent` |
| Hard threshold (default 69%, floor 10) | Pauses the next request locally, no upstream round-trip | `contextBudgetGuardHardPercent` |
| Model window overrides | A real observed ceiling always beats this package's built-in estimate | `contextBudgetGuardModelWindowOverrides` |

Two things worth knowing before you turn it on:

- **The window sizes are estimates, not published facts.** Per [the v2.5.0 notes](v2.5.0.md), the context window OpenAI's API docs advertise is not necessarily the one the ChatGPT Codex backend serves. Set `contextBudgetGuardModelWindowOverrides` once you have observed a model's real ceiling. A model the package has no estimate for is skipped rather than guessed at.
- **The pause is one-shot per measurement.** It cannot clear itself: a paused request never reaches upstream, so it can never produce a lower reading, and the `/compact` turn the notice asks for travels on the same session key. The guard therefore drops what it recorded as it emits the pause, so the next request is forwarded and re-measured. A session that really compacted comes back under the threshold and stays quiet; one that did not is paused again on the turn after.

The guard runs on both the plugin-loader fetch path and the default-on rotation proxy, keyed on the stable part of the session identity — the session or conversation header, `prompt_cache_key`, or a `metadata` id, never `previous_response_id`, which changes every turn and so could never accumulate. It no-ops entirely for a client that sends none of those, and while it is disabled it records nothing at all.

See [Context Budget Guard](../features.md#context-budget-guard-experimental) and the [settings reference](../reference/settings.md#experimental).

## Upgrade notes

No migration is required. Install the package and confirm the version:

```bash
npm i -g codex-multi-auth
codex-multi-auth --version
```

The command should report `2.10.0`.

Nothing changes for an unpinned pool, and the Context Budget Guard ships disabled: a `2.9.2` install that turns nothing on behaves the same, apart from a pinned request now retrying a transient failure instead of returning a 503 on the first one.
