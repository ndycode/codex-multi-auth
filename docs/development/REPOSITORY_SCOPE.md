# Repository Scope Map

What this repository contains, who owns each area, and what the project deliberately is not. Use this to decide where new code belongs — and where it does not.

* * *

## What This Repository Is

The **primary product** is the account manager plus the optional forwarding wrapper and runtime rotation proxy:

- the four published bins (`codex-multi-auth`, `codex-multi-auth-codex`, `codex-multi-auth-app-launcher`, `mcodex`),
- the `lib/` runtime those bins drive (storage, OAuth, rotation proxy, governance, manager commands),
- the five public export subpaths (`codex-multi-auth/auth|storage|config|request|cli` — see `docs/reference/public-api.md`),
- the test suite, and the user + maintainer docs under `docs/`.

## What This Repository Deliberately Is Not

- **Not a `codex` replacement.** No global `codex` bin is published; `codex-multi-auth-codex` forwards non-auth commands to the official CLI rather than reimplementing them.
- **Not a hosted service.** All state is local files under `~/.codex/multi-auth`; there is no multi-user server, no telemetry, no sync.
- **Not a patch of official Codex binaries.** The packaged-app path binds through user config + a localhost router and is reversible.
- **Not a plugin-host-only package.** `index.ts` (plugin entry), `.codex-plugin/plugin.json`, `config/*.json` templates, and `vendor/` exist for compatibility; they are not the primary surface.
- **Not a source of truth for historical claims.** `docs/releases/`, `docs/audits/`, `docs/development/implementation-plans/`, `docs/design/`, and `docs/benchmarks/` are snapshot material — accurate for the commit they were captured at, not current architecture guidance.
- **Not editable output.** `dist/` is generated by `npm run build`; `.tmp*`, coverage, and local caches are artifacts.

## Vendored Shims (`vendor/`)

`index.ts` still imports `Plugin`/`PluginInput`/`tool`/`Auth` from the original plugin-host packages. Rather than taking a real dependency, the repo vendors two type-only shims under `vendor/codex-ai-plugin/` and `vendor/codex-ai-sdk/`: `dist/index.js` files are intentionally near-empty (`export {}`) while `.d.ts` files supply the `any`-typed shapes; `tool.js` provides the identity `tool(def)` runtime used by `index.ts` registrations. `bundleDependencies` packs them into the npm tarball and `provenance.json` sha256-pins every vendored file (`npm run vendor:verify` enforces it). Do not "fix" them into real implementations — the emptiness is deliberate.

## Feature Placement Checklist

When adding a new feature:

1. Implement runtime/module code in `lib/` at the correct layer (`types/constants → storage → accounts → runtime → manager/CLI`; see [ARCHITECTURE.md](ARCHITECTURE.md#module-layering)).
2. Add/extend tests in `test/`.
3. Update user docs (`docs/features.md` + relevant guides).
4. Update `docs/reference/*` if a command, setting, or path changed.
5. Update [ARCHITECTURE.md](ARCHITECTURE.md) / [CONFIG_FLOW.md](CONFIG_FLOW.md) / [CONFIG_FIELDS.md](CONFIG_FIELDS.md) for cross-cutting behavior.
6. Update runtime-rotation docs when forwarded-Codex, shadow-home, proxy, app bind, or launcher behavior changes.
7. Update `docs/upgrade.md` and npm-script references when command flow or build steps change.
